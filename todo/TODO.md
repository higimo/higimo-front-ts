### 3. CSRF уязвимость при использовании JWT в cookies
TODO: [SECURITY]
В коде нет явной установки токена, но, судя по логике, сервер, вероятно, устанавливает httpOnly cookie после логина.
Проблема: Без защиты CSRF злоумышленник может отправить запрос от имени пользователя через подставной сайт (т.к. cookie отправятся автоматически).
Исправление на сервере:

Установите SameSite=Strict или Lax для cookie с токеном.

Используйте анти-CSRF токены (например, в заголовке X-CSRF-TOKEN).

Для критических операций (POST/PUT/DELETE) требуйте дополнительное подтверждение.

## 🟢 Оценка использования JWT в cookies
TODO: [SECURITY]
Хорошая идея, если соблюдены условия:

## Проблемы use Api

### Множественные useApi на одной странице без кэширования
Проблема: Три независимых запроса, которые не кэшируются между переходами. При каждом возврате на страницу они шлются заново.

Оптимизация: Использовать React Query (TanStack Query) или самодельный кэш на основе Map с TTL.

### Хуки форм дублируют бизнес-логику

📍 `hook/form/use-person-form.ts`, `use-meeting-form.ts`, `use-tag-form.ts`, `use-tag-group-form.ts`

Проблема: Все четыре хука имеют одинаковые поля: `status`, `isSubmitting`, `isSubmitted`, `resetForm`, одинаковую обработку ошибок (`ApiError`, `setError`), вызов API и т.д.

Решение: Создать фабрику `useEntityForm<T>`:

```ts
export function useEntityForm<T, D>({ api, isEditMode, onSuccess }) {
	const [status, setStatus] = useState([]);
	const [isSubmitting, setIsSubmitting] = useState(false);
	const [isSubmitted, setIsSubmitted] = useState(false);
	const formMethods = useForm<T>();

	const handleSubmit = useCallback(async (data) => {
		setIsSubmitting(true);
		try {
			const result = await (isEditMode ? api.update(data.id, data) : api.create(data));
			if (result.id) formMethods.setValue('id', result.id);
			toast.show('Сохранено');
			setIsSubmitted(true);
			onSuccess?.(result);
		} catch (error) {
			toast.error(error.message);
			setStatus(prev => [...prev, error]);
			if (error.errors) Object.keys(error.errors).forEach(key => formMethods.setError(key, error.errors[key][0]));
		} finally { setIsSubmitting(false); }
	}, [api, isEditMode]);

	const resetForm = useCallback(() => { if (!isEditMode) formMethods.reset(); setStatus([]); setIsSubmitted(false); }, [isEditMode]);

	return { formMethods, status, isSubmitting, isSubmitted, handleSubmit, resetForm };
}
```

### API-сервисы createOrUpdate копируют код

Проблема: В каждом классе метод createOrUpdate делает одно и то же: определяет метод (PUT/POST), строит endpoint, вызывает apiClient с compact(omit(obj, 'id')).

Решение: Базовый класс или функция-хелпер:

```ts
class BaseApiService {
	protected async createOrUpdate<T>(entity: Partial<T> & { id?: number }, routes: { create: string, update: (id: string) => string }) {
		const method = entity.id ? 'PUT' : 'POST';
		const endpoint = entity.id ? routes.update(entity.id.toString()) : routes.create;
		const { promise } = apiClient(endpoint, { method, body: compact(omit(entity, 'id')) });
		return promise;
	}
}
```

Использование:
```ts
class PersonApiService extends BaseApiService {
	async createOrUpdate(person: Partial<NokiaPersonSimpleType>) {
		return this.createOrUpdate(person, { create: API_ROUTE.personCreate, update: API_ROUTE.personUpdate });
	}
}
```

### Хуки useTags и useSmartTags частично пересекаются

Проблема: Оба управляют множественным выбором тегов. useTags проще, useSmartTags мощнее. Нет смысла держать два разных подхода.

Решение: Оставить только useSmartTags, а useTags переписать как обёртку над ним или удалить. Либо вынести общую логику работы с Set в отдельный хук useMultiSelect.

### Редиректы с backpath в разных местах

📍 LoginPage (использует getBackpath()), PrivateRoute (вызывает redirectToLogin с текущим path), а также в useAuth функция redirectToLogin формирует backpath.

Проблема: Логика сохранения и восстановления backpath размазана по трём файлам.

Решение: Создать сервис navigationService:

```ts
export const navigation = {
	saveBackpath() { sessionStorage.setItem('backpath', window.location.pathname); },
	getBackpath() { return sessionStorage.getItem('backpath') || ROUTE_LINKS.adminIndex; },
	redirectToLogin() { window.location.href = `${ROUTE_LINKS.login}?backpath=${encodeURIComponent(this.getBackpath())}`; },
	clearBackpath() { sessionStorage.removeItem('backpath'); }
};
```

Тогда и `PrivateRoute`, и `LoginPage`, и `useAuth` будут использовать один и тот же объект.

## 10 потенциальных улучшений в кодовой базе

### Включить `strict: true` в `tsconfig.json`
Сейчас `strict` закомментирован. Включение строгого режима TypeScript выявит потенциальные `null`/`undefined`, несогласованность типов и улучшит общую надёжность кода без дополнительных затрат на рефакторинг. Особенно полезно для проекта с большим количеством `@ts-ignore` и `any`.

### Внедрить E2E тесты (Playwright/Cypress)
Unit-тесты покрывают отдельные функции, но критический пользовательский сценарий – создание встречи, привязка персон, фильтрация тегов – не протестирован. Написать 3-5 E2E сценариев, которые запускаются в CI перед деплоем. Это предотвратит регрессии при рефакторинге форм и маршрутизации.

### Настроить `eslint-plugin-import` для порядка импортов
В файлах импорты перемешаны: сначала `preact`, потом `components`, потом `utils`, потом `dic`. Ввести правило `import/order` с группировкой (внешние библиотеки → алиасы → относительные пути). Это улучшит читаемость и сократит конфликты при слиянии веток.

### Генерировать API-клиенты из OpenAPI спецификации
Сейчас типы для API (`api-types/`) и маршруты (`API_ROUTE`) поддерживаются вручную. Это приводит к рассинхрону с бекендом. Если бекенд предоставит Swagger/OpenAPI, можно автоматически генерировать типы, эндпоинты и даже хуки (`openapi-typescript`, `@hey-api/openapi-ts`). Экономит часы разработки и исключает ошибки в DTO.

### Внедрить Service Worker для кэширования статики (PWA)
Проект – SPA, но при медленном соединении пользователь видит белый экран, пока загружается JS. Добавить `vite-plugin-pwa`, настроить стратегию кэширования (например, `StaleWhileRevalidate` для `/nokia/` и `CacheFirst` для ассетов). Это повысит производительность при повторных визитах и позволит работать офлайн (хотя бы для чтения).

### Централизовать управление модальными окнами через портал
Сейчас модальные окна (если есть) встроены в компоненты страниц. Для сложных форм (например, выбор персон во встрече) это создаёт проблемы с z-index, фокусом и передачей данных. Реализовать глобальный менеджер модалок на сигналах (`modalSignal`), который рендерит активное окно через `createPortal` в `body`. Модалка получает `onClose` и `onSubmit` через пропсы, а не через роутинг. Это упростит переиспользование форм.

### Оптимизировать загрузку шрифтов и CSS (critical CSS)
В `style.css` импортируется весь CSS глобально. Использовать `vite-plugin-critical` или `@loadable/component` для инлайна критических стилей (шапка, карточки встреч) и отложенной загрузки остальных. Для шрифтов добавить `preconnect` и `font-display: swap` в заголовок. Это улучшит First Contentful Paint и метрики Core Web Vitals.

## 10 архитектурных улучшений

### Переход от `react-hook-form` к сигналам для управления формами
**Проблема**: `react-hook-form` завязан на React Context и вызывает лишние ререндеры при изменении полей. В `NokiaMeetingFormContainer` используется `FormProvider`, что усложняет передачу состояния в модальные окна.
**Решение**: Разработать собственную лёгкую систему форм на сигналах (как описано в предыдущих ответах). Это даст прозрачную реактивность, простую интеграцию с модалками и полный контроль над валидацией.

### Переход к Feature-Sliced архитектуре (FSD)
**Проблема**: Код разбит по техническим слоям (`components/ui`, `hook`, `services`), но фичи размазаны. Например, логика создания встречи находится в 5+ папках: `components/form/nokia-meeting-form-*`, `hook/form/use-meeting-form`, `services/meeting-api`, `pages/meeting-create-page`.
**Решение**: Сгруппировать код по фичам: `features/meeting/{ui,model,api,lib}`. Это улучшит локальность изменений и позволит легко удалять/перемещать целые фичи.

### Выделение слоя кэширования и синхронизации (TanStack Query)
**Проблема**: `useApi` не кэширует данные и не инвалидирует их при мутациях. После создания новой встречи список встреч не обновляется автоматически.
**Решение**: Внедрить `@tanstack/react-query` (совместим с Preact). Настроить автоматическую инвалидацию ключей по тегам (например, `['meetings']`). Это уберёт ручное управление состоянием загрузки и ошибок, а также сократит количество запросов.

### Унификация маршрутизации через роутер на сигналах
**Проблема**: Используется `preact-iso`, который хорошо работает, но интеграция с сигналами отсутствует. `useRoute` вызывает ререндер всех подписчиков.
**Решение**: Создать собственный роутер на сигналах (например, через `preact-router` + обёртка). Хранить текущий путь в сигнале, подписываться на него точечно. Компоненты, которым нужен только `path`, не будут перерендериваться при изменении query-параметров.

### Выделение диалогового менеджера (модальные окна)
**Проблема**: В проекте нет унифицированного способа открытия модальных окон. Сейчас формы редактирования открываются на отдельных страницах. Для улучшения UX (например, быстрая правка персоны из встречи) нужны модалки.
**Решение**: Создать глобальный `DialogStack`, работающий через сигналы. Любой компонент может вызвать `dialogs.open(MyForm, { props })`. Модалка рендерится через портал, поддерживает стек и анимации.

### Автоматическая генерация типов и API-клиентов из OpenAPI
**Проблема**: Типы в `api-types/nokia.types.ts` и маршруты в `API_ROUTE` поддерживаются вручную, что ведёт к рассинхронизации с бекендом.
**Решение**: Добиться от бекенда OpenAPI спецификации (Swagger). Использовать `openapi-typescript` для генерации TypeScript типов и `@hey-api/openapi-ts` для создания SDK. Удалить `api-types` и `dic/API_ROUTE`, заменив на автосгенерированный код.

### Внедрение событийно-ориентированной коммуникации между фичами
**Проблема**: После успешного создания встречи мы хотим обновить статистику, список встреч, уведомить другие компоненты. Сейчас это делается через `toast` и ручной редирект.
**Решение**: Внедрить шину событий (event bus) на сигналах. Публиковать события типа `meeting:created`, `person:updated`. Подписчики (другие фичи) могут реагировать, например, инвалидировать кэш или показывать нотификацию. Это ослабит связанность между модулями.

## 5 мест, где неудобно работать с бекендом (и вы можете это исправить на сервере)

### Нет массового создания/обновления тегов для персоны
**Проблема**: В `PersonCreatePage` и `PersonReadPage` нет возможности привязать/отвязать теги у персоны. API бекенда, судя по типам, позволяет это делать, но в клиентском коде отсутствует UI. При этом в API_ROUTE есть `personAttachTags` и `personDetachTags`.
**Решение на сервере**: Сделать эндпоинт `PATCH /api/person/:personId/tags`, который принимает массив `tag_ids` и полностью заменяет набор тегов у персоны (или добавляет/удаляет по флагу). Это упростит клиентскую логику (не нужно вызывать два метода для синхронизации). Также добавить валидацию существования тегов и персоны.

### Отсутствие пагинации на списках
**Проблема**: Эндпоинты `/api/meetings`, `/api/person`, `/api/tags` возвращают все записи разом. Со временем данных станет много (сотни встреч, тысячи персон), и фронтенд будет тормозить.
**Решение на сервере**: Добавить параметры `?page=1&limit=20` и `?offset=0&limit=20` для всех коллекций. Вернуть также `X-Total-Count` заголовок или объект `{ data: [], meta: { total, page, limit } }`. На клиенте реализовать бесконечную прокрутку или пагинацию.

### Нет поиска/фильтрации на стороне сервера
**Проблема**: Сейчас фильтрация персон по тегам происходит на клиенте (`filterTagAndGroupsStrategy`). При большом количестве данных это медленно. Также нет поиска по имени/алиасу.
**Решение на сервере**: Добавить query-параметры: `?tag_id[]=1&tag_id[]=2` (AND/OR логику можно реализовать через `?tags_mode=all`), `?search=Иван`. Это снизит нагрузку на клиент и ускорит отклик.

### Даты возвращаются в разных форматах
**Проблема**: В типах есть `ISOString`, `DateOnlyString`, `DateTime`, `UnixTime`. В реальных ответах API поле `date` у встречи приходит как строка `"2025-12-12"`, а `date_start` – как `"2025-12-12T00:00:00+03:00"`. Нет единого стандарта, из-за чего клиент вынужден использовать костыли (`toMoscowDateTime`, ручной парсинг).
**Решение на сервере**: Унифицировать все даты до ISO 8601 с UTC (например, `2025-12-12T00:00:00Z`). Если нужно локальное время – передавать смещение отдельно. На клиенте тогда можно будет использовать стандартный `new Date()` без дополнительных преобразований.

### Нет endpoint для получения статистики по тегам персон
**Проблема**: На странице статистики сейчас только встречи по типам и годам. Нет аналитики: сколько встреч с человеком, у которого есть тег `"друг"`, или распределение встреч по тегам персон.
**Решение на сервере**: Создать эндпоинт `GET /api/statistics/person-tags`, который возвращает `{ tag_title: string, meeting_count: number }[]` за выбранный период. Это позволит строить круговые диаграммы и выявить, с кем и по каким темам чаще всего общаетесь.

## 5 мест, где можно (и нужно) использовать хуки, но пока нет

### Управление модальными окнами / диалогами (`useDialog`)
**Где сейчас**: В проекте нет унифицированного подхода к модальным окнам. Формы открываются на отдельных страницах, но в будущем для улучшения UX (например, быстрая правка персоны из встречи) понадобятся модалки.
**Почему не хук**: Логика открытия/закрытия, передача данных и обработка результата размазана бы по компонентам.
**Как должно быть**:
```ts
const { open, close, isOpen, data, result } = useDialog();
open(MyForm, { initialData: person });
result.then(updatedPerson => ...);
```

### Подписка на глобальные события (тосты, сообщения) (`useEventBus`)
**Где сейчас**: В `ToastContainer` и `MessageContainer` есть `useEffect` с ручной подпиской на `window` события. Также в `useToast` и `useMessage` есть дублирование.
**Почему не хук**: Логика подписки и отписки, управление очередью сообщений повторяется.
**Как должно быть**:
```ts
const { emit, on } = useEventBus();
emit('toast:show', { message: 'Сохранено', type: 'success' });
on('toast:show', (payload) => addToast(payload));
```

### Проверка авторизации с редиректом (`useAuthRedirect`)
**Где сейчас**: В `PrivateRoute` и `LoginPage` повторяется логика:
```ts
if (!isAuth) redirectToLogin();
if (isAuth) redirectToDashboard();
```
**Почему не хук**: Усложняет тестирование компонентов, завязывает их на конкретный роутинг.
**Как должно быть**:
```ts
useAuthRedirect({
	redirectIfNotAuth: '/login',
	redirectIfAuth: '/admin',
	loadingFallback: <Loading />
});
```

### Сохранение состояния сворачивания секций в `localStorage` (`usePersistedState`)
**Где сейчас**: В `CollapseSection` состояние `folded` теряется при перезагрузке. Пользователь каждый раз заново раскрывает нужные блоки.
**Почему не хук**: Логика чтения/записи в `localStorage` и синхронизации с `useState` засоряет компонент.
**Как должно быть**:
```ts
const [folded, setFolded] = usePersistedState('collapse-section-meetings', false);
ключ уникален для каждой секции (например, по заголовку)
```
